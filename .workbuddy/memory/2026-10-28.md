### Supabase 共享数据库支持（提交 691c1c7）

用户需求：与合作用共用一个 Supabase，代码拉取后双方数据互通。

**关键发现：schema.sql 头部就写着「PostgreSQL 15+（Supabase 实测 PG 17）」**——
合作用做 PG 迁移时已在 Supabase 上验证过建表脚本；pg_trgm 是 Supabase 内置扩展；
种子/回归脚本的 LZ_PG_SSLMODE 默认 require。**兼容性零改动，只差连接配置。**

实现（cloud profile 方案，不动 local）：
- `application-cloud.yml.example` 新模板：cloud 覆盖数据源（Supabase Session pooler +
  sslmode=require）+ 两个**必须两机一致**的共享密钥（lz.security.jwt.secret、
  lz.attendance.qr-sign-secret）
- 启动：`--spring.profiles.active=local,cloud`（later profile 覆盖 earlier，
  Redis/LLM/地图 Key 仍用各自 local）；去掉 `,cloud` 即切回本机 Docker 库
- `.gitignore` 加 application-cloud.yml；docs/shared-supabase.md 七节完整指引
- 本机 tasks.json（gitignore）加了「dev: 后端（云端库 Supabase）」任务

**两个跨机密钥坑（为什么必须共享密钥）**：
1. JWT secret 不同 → A 签发的登录 token 在 B 后端直接 401
2. qr-sign-secret 不同 → A 后台签发的场所二维码在 B 后端被 HMAC 校验判"伪造"
（真实场景：管理后台在 A 机生成码，员工手机 BASE_URL 指向 B 机）

**连接串要点**：必须用 Session pooler（aws-0-<region>.pooler.supabase.com:5432，IPv4）；
db.<ref>.supabase.co 免费版 IPv6-only 连不上；Transaction pooler 6543 不支持
JDBC 会话语义。用户名带项目前缀 `postgres.<ref>`。

**双缓存注意**：两后端各连本机 Redis，A 写库不会失效 B 的缓存，等 TTL
（统计 60s / 场所详情 600s）。免费版 7 天不活跃自动暂停，答辩前要 Restore。

**初始化警示**：schema.sql 含 DROP TABLE IF EXISTS，只能由一人执行一次，
另一人再跑会清空全部数据（文档里加粗强调）。

### Supabase 实际接入跑通（朋友 eb7c198 之后，提交 443794c）

朋友建好了 Supabase 并写了《接入共享 Supabase 数据库》指引（含连接串/口令/两密钥），
我按指引在本机配置并跑通。连接信息（gitignore 的 application-cloud.yml）：
Session pooler `aws-0-ap-northeast-2.pooler.supabase.com:5432`(首尔)，
用户 `postgres.nxvomwfjzrrbfciwvtil`，PG 17.11，public schema 25 表，
6 员工（含朋友建的"王溪"）/ 96 打卡 / 3 场所 / 4 知识库文档。

**踩坑 1：首次连接必超时**。application.yml 的 `druid.max-wait=5000` 对本地库够用，
但连 Supabase **首次**连接含 TLS 握手 + JVM 安全随机数初始化，实测 5 秒出头
（之后稳定 1~2s）→ 启动后第一次 health 显示 `connected=false`、刷新才 true。
修：application-cloud.yml(.example) 里把 `spring.datasource.druid.max-wait` 放宽到 15000，
只影响 cloud profile。**改模板而非只改本机文件**，朋友拉到同样生效。

**踩坑 2（修朋友的 eb7c198）**：start-backend.cmd 的 cloud 分支
`set "PROFILE_ARG=%PROFILE_ARG%,cloud"` 在 application-local.yml 缺失时 PROFILE_ARG 为空
→ 传给 java 的是 `,cloud`（非选项参数被 Spring 静默忽略）→ cloud 不生效却启动成功，极难排查。
已改成分情况：为空时单独设 `--spring.profiles.active=cloud`。

**诊断手法（可复用，分层定位很有效）**：
TCP 连通 → psycopg2 直连（1.06s，验证凭据/表）→ 独立 JDBC 小测试（1856ms，
验证驱动/URL）→ 应用 health。三层都过说明只剩应用层配置问题。
注意：javac 在中文 Windows 默认 GBK，脚本含中文要加 `-encoding UTF-8`；
java -cp 必须用 `C:/...` 形式，MSYS 的 `/c/...` 路径 Java 不认（报 No suitable driver）。

**瞬时抖动**：中途出现过一次 `PSQLException: 尝试连线已失败`，随后自动恢复——
Druid `break-after-acquire-failure` 默认 false 会重试，非致命，答辩遇别慌，刷新即可。

**当前运行状态**：后端 8080（local,cloud 连 Supabase）+ 前端 5173 均已启动，
health connected=true，admin 登录正常，/api/employees 返回 6 人。
