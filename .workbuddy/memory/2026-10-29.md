### 修编辑员工改工号不生效（提交 7dd9f60）

**现象**：编辑员工 LZ0007→LZ0008，提示"更新成功"，但列表和 Supabase 库里都是旧值。

**根因**：`EmployeeMapper.xml` 的 `updateById` 动态 set **漏了 emp_no 列**——
Service 层专门写了工号唯一性校验（countByEmpNo+excludeId），说明本意支持改工号，
是 SQL 漏字段静默丢弃修改。返回 R.ok() 所以前端显示成功，最难察觉的一类 bug。

**连带修掉更危险的隐患**：前端 openEdit 把 empNo 重置为 ''（占位文案"留空表示不修改"），
而 MyBatis `<if test="empNo != null">` 对空串也成立 → **留空提交会把 emp_no 清空成 ''**。
修法：Mapper 条件改 `empNo != null and empNo != ''`；openEdit 回填 row.empNo。

**数据安全性确认**：emp_no 仅 hr_employee 一表（唯一索引 uk_emp_no），考勤等表以
employee_id 关联 → 改工号不影响历史数据，可以放心开放编辑。

**验证**（local,cloud 连 Supabase）：PUT id=7 empNo=LZ0008 → code=0；接口回读 LZ0008；
psql 直查 DB emp_no='LZ0008'；反面验证 empNo 留空提交后 emp_no 仍为 LZ0008 未被清空。
用户想改的 LZ0008 已顺带生效（李四 id=7）。

**排查手法**：MyBatis 动态 SQL "更新成功但没生效"先查 XML 的 <set> 里有没有那一列——
实体有字段、Controller/Service 链路正常不代表 SQL 会更新它。

### 员工"离职"改为物理删除、移除复职（提交 09fece0）

需求：离职 = 整条记录从档案消失 + 数据库行删除，不再是 status=0。

**实现**：
- Controller：`POST /{id}/status`（changeStatus）→ **`DELETE /{id}`**，权限沿用 hr:employee:update（不新增权限码）
- Service.delete：@Transactional 先清关联再删档案行——**全库无外键约束**（schema.sql 零 FOREIGN KEY），
  必须手动清理 5 张关联表：face_feature / biz_application / att_daily_stat / att_record / hr_employee_place；
  sys_user.employee_id 与 org_department.leader_employee_id 置 NULL（账号保留、不再任部门负责人）
- 前端：删掉"状态"筛选和状态列（列表不再有离职行）；"离职/复职"二态按钮 → 单一红色"离职"，
  确认弹窗警示"不可恢复、无法复职"；api 换 deleteEmployee

**设计取舍说明（答辩可能被问）**：原设计保留离职状态是为"历史考勤不失真"（Service 类注释里就写着），
现按需求改为连带清理历史数据——删除语义更直观，但失去离职历史。朋友 0648b3c/1984330
（阿里云 FC 部署）同期合入，无冲突。

**验证**：DELETE /api/employees/7（李四）→ code=0；接口回读空；psql 直查 id=7 剩 0 行。
**注意**：李四工号显示回 LZ0007——是朋友在共享库上改回去的（不是 bug）。

### 修地图选址搜索永远"未搜索到相关地点"（2026-10-29 上午）

**现象**：地图选址弹窗/地图正常，搜任何关键词必弹"未搜索到相关地点"。

**排查过程（方法比结论更值钱）**：
- 先怀疑 Key/安全密钥：REST 直连 `restapi.amap.com/v3|v5/place/text` 带 jscode
  返回 `USERKEY_PLAT_NOMATCH`（10009）——**这是误导**：JS API 类型 key 本就不许打
  Web 服务 REST，报平台不匹配是预期行为，不能据此定罪
- 正确手法：**playwright-core + 系统 Edge（channel:'msedge'，免下载内核）无头实测**。
  npm 装 playwright-core 遇 npmjs 网络失败，换 `--registry=https://registry.npmmirror.com` 即过
- 实测真相：**key/scode 完全有效，搜索成功返回 61 条**——问题纯在 frontend

**根因（JS API 1.4 → 2.0 两个断代差异叠加）**：
1. `PlaceSearch.search()` 在 2.0 **不返回 Promise**（返回 undefined）——
   `await placeSearch.search(kw)` 等于 await undefined → 永远"未搜索到"。必须回调式
2. 结果结构 2.0 是 `res.poiList.pois`（1.4 才是顶层 `res.pois`）；
   status=complete 时 info=OK，读错字段**不报任何错**

**修法**：doSearch 改回调式包 Promise；complete → poiList.pois；error → 把
res.info（如 INVALID_USER_SCODE）透传到提示，不再吞错。

**验证**：无头浏览器逐行复刻修复后逻辑，"郑州轻工业大学"返回 10 条
（东风校区/科学校区…），LngLat 两种取值方式（getLng()/lng）都兼容。
前端 Vite 热更新即生效，无需重启。
