# uni-app / 小程序方案评估（阶段 6）

> 定位：项目总指令对移动端的表述是「H5 响应式完善；uni-app **视时间评估**，不承诺未完成的小程序」。
> 本文只做评估，**不产出可运行的小程序代码**。结论必须与当前仓库实际状态一致，
> 不把"理论上可行"写成"已经具备"。

## 1. 当前移动端现状（事实）

| 能力 | 现状 | 位置 |
|---|---|---|
| 扫码打卡页 | 已完成，支持摄像头扫码 + 手动输入兜底 | `web/src/views/h5/Checkin.vue` |
| 人脸打卡页（模拟） | 已完成，明确标注 `mock=true` | `web/src/views/h5/FaceCheckin.vue` |
| H5 独立路由 | `/h5/checkin`、`/h5/face`，无需登录即可访问 | `web/src/router/index.js` |
| 摄像头扫码 | 依赖 `html5-qrcode`（浏览器 `navigator.mediaDevices`） | `Checkin.vue` |
| 定位与围栏 | 浏览器 `geolocation`，拿不到坐标时不参与判定（不伪造） | `Checkin.vue` |
| 响应式 | 视口自适应、安全区、触控目标 ≥44px、横屏与窄屏适配 | 本次阶段 6 补齐 |
| 后端接口 | REST + JWT Bearer，与端无关 | `server/lz-*` |

也就是说：**在不引入 uni-app 的前提下，移动端链路已经闭环**——手机浏览器或企业微信/微信内置浏览器打开 `/h5/checkin` 即可完成打卡。

## 2. 若改为 uni-app，能复用什么

| 层次 | 能否复用 | 说明 |
|---|---|---|
| 后端全部接口 | ✅ 完全复用 | REST + JWT，端上只换存储与请求客户端 |
| 业务逻辑（打卡校验链、幂等、围栏） | ✅ 完全复用 | 都在服务端，端上不重复实现 |
| Pinia 状态管理 | ✅ 可复用 | uni-app 支持 Pinia |
| API 封装层（`web/src/api/*.js`） | ⚠️ 需改造 | 基于 axios；小程序端没有浏览器的 XHR，需换 `uni.request` 或加适配器 |
| 页面模板与排版 | ⚠️ 部分复用 | 结构与样式大体可搬，但组件要换 |
| ElementPlus 组件 | ❌ 不可用 | 依赖 DOM 与浏览器 API，小程序端无 DOM；需换 `uni-ui` / `uView` |
| `html5-qrcode` 扫码 | ❌ 不可用 | 依赖 `navigator.mediaDevices`；小程序端须用 `uni.scanCode` 或 `<camera>` 组件 |
| vue-router | ❌ 不可用 | 改用 `pages.json` 声明式路由 |
| `localStorage` 存 token | ❌ 不可用 | 改用 `uni.setStorageSync` |
| 浏览器 `geolocation` | ⚠️ 需改造 | 改用 `uni.getLocation`，且要在 `app.json` 声明定位用途、通过平台审核 |

结论：**真正能直接搬过去的只有"后端接口 + 服务端逻辑"**，前端部分等同于按小程序范式重写一遍。

## 3. 改造成本估算

| 工作项 | 规模 | 说明 |
|---|---|---|
| 工程搭建（uni-app + HBuilderX/CLI、双端配置） | 0.5 天 | 含 `pages.json`、`manifest.json` 配置 |
| 请求/登录/存储层改造 | 1 天 | axios → `uni.request`，token 存储迁移，401 处理 |
| 扫码打卡页重写 | 1 天 | `uni.scanCode` + 手动输入兜底 + 定位授权流程 |
| 人脸页重写 | 0.5 天 | 目前是模拟层，改造难度低但价值也低 |
| 样式与组件迁移 | 1 天 | ElementPlus → uni-ui，含表单、弹窗、结果卡片 |
| 真机联调与权限适配 | 1 天 | iOS/Android 定位、摄像头权限、HTTPS 与域名白名单 |
| **合计** | **约 5 人日** | 不含小程序资质与审核等待时间 |

## 4. 风险与前置条件（不是技术问题，但会直接卡住交付）

1. **小程序主体资质**：企业考勤类小程序需要**企业主体**认证；个人主体无法上线这类服务。当前项目没有可用的 AppID 与主体信息。
2. **域名与备案**：小程序 `request` 合法域名必须是已备案的 HTTPS 域名，本地演示的 `127.0.0.1:8080` 与局域网地址不能用；真机调试需临时开启"不校验合法域名"，不能用于上线。
3. **定位权限审核**：使用 `uni.getLocation` 需要在小程序后台填写用途说明并通过审核。
4. **人脸能力**：当前是模拟适配层（见 `docs/face-sdk-integration.md`）。小程序端若要做真实人脸核验，要么接微信实名/活体能力，要么接第三方 SDK，属于额外授权与费用，不在本项目范围内。
5. **C 盘空间**：本机 C 盘仅剩约 9 GB，uni-app 工具链（HBuilderX、模拟器、node_modules）会额外占用数 GB，清理前不具备安装条件。

## 5. 结论与建议

- **阶段 6 不产出小程序**。当前 H5 已能覆盖移动端演示与真实使用（浏览器/微信内置浏览器打开即可），引入 uni-app 的边际收益低于其资质与工期成本。
- 如果后续确实需要小程序（例如要接入微信生态的扫码入口、或用户不接受浏览器打卡），建议按以下顺序推进：
  1. 先确认企业主体 AppID 与已备案 HTTPS 域名（这是硬前置，缺一项就不要开工）；
  2. 只迁移**扫码打卡**一个页面（人脸页价值低且是模拟实现）；
  3. 后端接口一行不改，只做请求层与存储层适配；
  4. 保留 H5 版本作为兜底，两套并存而不是替换。
- **不做的理由必须如实呈现**：小程序不是"H5 打包一下就能上"，ElementPlus、html5-qrcode、vue-router、localStorage 四项在小程序端全部不可用，前端等同于重写。

## 6. 与答辩口径的关系

答辩时若被问到"为什么不做小程序"，可直接引用本文第 2 节与第 4 节：
技术上是"前端需重写而非复用"，非技术上是"缺企业主体与备案域名"，
两者都不是本项目阶段 6 能解决的事项，因此按总指令要求"不承诺未完成的小程序"。
