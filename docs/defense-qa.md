## A. 架构选型

### A-1 为什么用单体，而不是微服务？

1. 这是权衡结果，不是"不会做微服务"。系统按业务拆成了 11 个 Maven 模块，边界是按可拆分的方式划的。
2. 判断依据是**体量与团队规模**：考勤系统日活有限、模块间调用频繁，引入注册中心、网关、分布式事务、链路追踪后，
   增加的运维复杂度远超收益，还会引入网络不可靠性这个新的故障来源。
3. 但**预留了升级路径**：业务模块之间不编译依赖（跨模块读表统一走 `XXXSupportMapper` 约定），
   Nacos 依赖已登记但未引入，因此"将来分成本地服务"不需要重写业务逻辑，改的是部署形态。
4. 一句话：**单体不是落后，微服务也不是先进，选择要匹配问题规模。**

### A-2 模块是怎么拆的？会不会拆得太细/太粗？

1. 按业务能力拆分：`lz-system`（账号权限）、`lz-place`（场所）、`lz-attendance`（考勤核心）、
   `lz-knowledge`（知识库）、`lz-face`（人脸）、`lz-file`（文件）、`lz-job`（任务），
   外加 `lz-common`（无依赖基础件）和 `lz-framework`（框架层：AOP、鉴权、缓存）。
2. `lz-framework` **不反向依赖任何业务模块**——比如权限查询的契约定义在 framework，
   实现放在 system（`PermissionCheckerImpl`），用依赖倒置避免循环依赖。
3. 粒度标准是"单一职责 + 能否独立演进"，而不是按技术分层拆。

### A-3 为什么选 Spring Boot 3 + Vue 3 + Element Plus？

- Spring Boot 3 是目前主流 LTS 路线，生态成熟，Java 17 有更好的性能与新语法；
- Vue 3 组合式 API + Pinia 状态管理，开发效率和可维护性平衡较好；
- Element Plus 组件齐全，后台管理场景不必重复造轮子；
- **MySQL 全文检索（ngram）**这条技术选型尤其关键：中文分词不必额外引入 Elasticsearch，
  在校园项目的体量下够用且运维成本低——这一点如果被追问，可以讲权衡过程。

## B. 核心业务（CPT90 三条链路）

### B-1 员工建档这条链路做了什么？

组织架构建公司 → 建部门 → 建岗位 → 员工管理录入员工（工号自动生成且唯一）→ 办公场所绑定员工。
每一步都有服务端校验：重复工号被唯一约束挡住（`40901` 并提示工号名），删除有在职员工的部门会被拒绝
（提示"该部门下仍有在职员工"）。员工离职是**停用而非物理删除**，历史考勤才查得到。

### B-2 二维码为什么不能只放一个自增 ID？

1. 二维码一旦生成就会被**截图、转发、拍照**，属于完全不可控的公开信道。
2. 只放主键意味着任何人把 ID 加 1，就能伪造出另一个场所的合法二维码。
3. 本系统用 **明文参数 + HMAC-SHA256 服务端签名**：参数可以被看见，但改任何一个字符签名就对不上，
   服务端校验直接拒绝。签名用 `MessageDigest.isEqual` 做常量时间比较，不用字符串 `equals`（后者在首个不同字符处就返回，会泄露"前几位猜对了"的信息）。
4. 二维码还要过一道校验链：签名 → 是否存在 → 是否作废 → 是否过期 → 是否本场所 → 是否重复 → 围栏。

### B-3 员工站在门口打卡算不算到岗？围栏怎么判的？

1. 用 **Haversine 球面距离**算员工上报坐标与场所坐标的直线距离，超过半径就拒绝并**回显实测距离**。
2. 关键细节：坐标缺失时返回 `null` 而**不是 0**。演示环境手动录入坐标，为空是常态；
   如果返回 0，等于"没配坐标的场所把所有人的打卡都判为围栏内"，这是放大型错误。
3. 员工没上报坐标时不拦——因为浏览器定位可能失败，此时用手动输入通道兜底。

### B-4 数据权限是怎么收敛的？

1. 三档：`ADMIN` 全量、`DEPT` 本部门、`SELF` 仅本人，由服务端 `DataScopeResolver` 判定。
2. **收敛在服务端做**，前端传什么参数都不影响结果——演示时可以改前端请求里的 `deptId`，
   服务端会强制覆盖成调用者自己的部门。
3. 员工始终坚持一点：**统计接口不能比记录接口看到更多**，两者共用同一套口径。

### B-5 出勤率怎么算？休息日算不算缺勤？

1. 工作日人天 = 总人天 − 休息日人天，**分母不含休息日**，否则周末会拉低出勤率。
2. 出勤人天 = 正常 + 迟到 + 早退（迟到早退算到了岗但不算正常）；缺勤另行统计。
3. 出勤率 = 出勤人天 / 工作日人天。
4. 这些口径都是单元测试锁死的（`StatisticsServiceTest` 有一条专门验证"休息日不计入分母"）。

### B-6 日汇总为什么幂等？重复跑会不会出问题？

1. 依赖 `(employee_id, stat_date)` 唯一键做 `ON DUPLICATE KEY UPDATE`，重复重算只刷新不新增。
2. 踩过一个坑：MySQL 的返回值有三态（插入返回 1、更新且值变化返回 2、值无变化返回 0），
   用它当"影响行数"会让两次重算的数字不一致（实测 168 → 90），看起来像幂等被破坏。
   **改为按覆盖员工数统计**，数字稳定。
3. 重算后立刻 `evictByPrefix("statistics:")` 清看板缓存，避免"点了重算但页面没变"。

### B-7 知识库检索为什么不用 Elasticsearch？

1. 体量不大（学校场景的文档规模），引入 ES 意味着额外的部署、分词器配置、索引同步开销。
2. MySQL 5.7 支持 **ngram 全文索引**，`ngram_token_size=2` 正好适合中文二元分词，够用且运维简单。
3. **权限过滤写在 SQL 的 WHERE 里**，不是查完再在内存里筛——否则分页大小和权限都可能出错。
4. 已知边界：MySQL 5.7 的 InnoDB 全文索引对刚插入的行有极短缓存合并时延，连续上传后立刻检索可能偶发漏命中，重试即可。

## C. 核心三问（务必主动交代）

### C-1 人脸识别为什么是模拟的？

1. 虹软 ArcSoft SDK 需要**商业授权和产品密钥**，课程周期内确实拿不到，这是事实。
2. 所以做了**可插拔设计**：`FaceRecognitionService` 接口 + `NoopFaceRecognitionService` 模拟实现 +
   `ArcSoftFaceRecognitionService` 条件装配（缺 SDK 时明确报错而不是崩溃）。
3. 每一层都**显式标注**：接口返回 `mock=true`，服务端日志带 `[MOCK]` 前缀，页面上写明"(模拟)"。
4. **考勤以二维码打卡为准**，人脸只是一条核验通道，所以它的模拟状态不会影响核心业务的真实性。
5. 真实接入的改造清单写在了 `docs/face-sdk-integration.md`——不是"做不了"，是"有条件就能接"。

> 这句话很关键：**宁交一卷写着"模拟"的答卷，也不交一份假装成真的系统。**

### C-2 有 AI 大模型吗？为什么感觉它只是搜索？

1. 没有可用的大模型 API Key，因此当前是 **retrieval-only 模式**：只做检索，把最相关的原文片段和出处返回给用户。
2. 这是刻意的设计底线：**有 Key 就在这基础上叠加生成能力，没有 Key 就老实做检索**。
3. 检索不到时直接返回"未找到足够依据"，**绝不让它编造制度的条款**——考勤制度这种内容，编一句就可能误导员工。
4. `LlmClient` 是可插拔接口，配上 Key 后会自动切换到 OpenAI 兼容实现，**但"无命中不编造"这条规则不变**。

### C-3 地图服务也没接吗？

1. 没接，坐标是手动录入的。
2. 这一点系统在两个地方如实上报：接口返回 `enabled=false, provider=none, coordinateSource=manual-input`，
   「系统与依赖状态」页面也写明未启用。
3. 围栏校验仍然可用（基于 Haversine 球面距离），缺的只是地图可视化——不影响功能完整性。

## D. 工程质量

### D-1 你怎么证明系统真的能跑，而不是堆了一堆文档？

1. 单元**64 项**、接口回归**128 项**，共 192 项真实执行通过，一条 `npm run verify` 复现。
2. 容器不是"产出清单"而是**真跑过**：Docker Compose 四容器 healthy、kind 集群四 Pod Running、
   GitHub Actions 用 act 本地实跑两个 job。
3. 打包流程不允许 `-DskipTests`——测试不过就打不出 jar。
4. 「系统与依赖状态」页实时上报外部依赖的真实状态，可以现场打开看。

### D-2 测试都是自己点的吗？覆盖哪些？

1. 自动化测试 **192 项**（单元 64 + 接口回归 128），覆盖核心算法、安全判定、全链路业务与各类失败场景
   （越权、篡改、重复、过期、超围栏、作废、跨部门下载）。
2. 特别说明：**重点把"写错也能正常返回"的逻辑写成单元测试**——缓存键是否含数据范围、
   文件可见范围判定、二维码签名校验，这三类出问题时功能测试发现不了。
3. 诚实边界：前端 UI 无 E2E 测试，未做并发压测，真机兼容性只在模拟器 + 响应式规则层面验证。
   这些都写进了 `known-issues.md`。

### D-3 演示数据会不会是假的？怎么区分？

1. 演示流水全部带 `source='SAMPLE'` 标记、requestId 以 `SAMPLE-` 前缀开头，**可一键删除**。
2. 所有统计接口返回 `dataSource` 字段：`real` / `mixed` / `sample` 三档，界面上有对应徽标。
3. 演示补录数据由脚本 `scripts/seed-sample-attendance.mjs` 生成，共 14 天约 94 条；
   什么时候补的、范围是多少，在 `progress.md` 里逐条留了记录，不存在偷偷塞数据的情况。

### D-4 你遇到的最大困难是什么？（建议挑一个真实的）

推荐讲这条：**"重算后看板数字不刷新 / 首次部署后看板全 0"**。

1. 现象：容器第一次起来时，`att_daily_stat` 是空的，看板全 0；管理员点了「重新计算」，数字还是没变。
2. 排查：初始化脚本只插了打卡流水，没算日汇总；而重算接口**不带日期参数时只算当天**，
   演示流水落在过去 14 天，压根没进统计。
3. 修复：改成按"最早一条打卡流水 ~ 今天"自动推导重算区间；同时确认重算后主动清理看板缓存前缀。
4. 收获：**"能跑"和"跑出来的结果是对的"是两件事**，部署脚本必须把数据初始化和应用层计算一起考虑；
   这类缺陷只有在真跑容器时才会暴露，光看代码看不出来。

### D-5 缓存和数据库会不会不一致？Redis 挂了怎么办？

1. 缓存是**开关化**的：`lz.cache.enabled=false` 时降级为直查，应用完全不依赖 Redis。
2. Redis 连续失败 3 次会**熔断 30 秒**，期间走直查，不会拖垮主链路。
3. 一致性靠三处保障：**短 TTL**（看板 60 秒）、**写操作主动失效**（场所更新即清）、**重算后按前缀清理**。
4. 缓存键**必须包含数据范围**（`:dept=xx:emp=xx`），否则部门主管会命中管理员缓存下来的全量数字——
   这是把"性能优化"写成"越权读取"的经典陷阱，已用单元测试锁死。

## E. 安全

### E-1 越权是怎么防的？

1. 接口级：`@RequirePermission` 注解 + 拦截器；权限不足返回 `40301`。
2. 数据级：`DataScopeResolver` 服务端收敛，前端传参无效。
3. 文件级：三档可见范围（PUBLIC / DEPT / PRIVATE）+ `file:admin`。
   越权下载会**写 `log_operation` 留痕**，并且响应不回显文件是否存在（防探测）。
4. 缺失字段的默认值是**收紧而不是放开**：可见范围为空时按 PRIVATE 处理，部门为空的 DEPT 文件退化为仅上传人。

### E-2 文件上传有什么安全措施？

1. 下载**只接受 id，不接受任何路径参数**，从根上杜绝 `../` 目录穿越。
2. 服务端 **UUID 重命名**，原始文件名只用于展示；解析后的路径会再做一次越界校验。
3. 响应**不带存储路径**，列表接口返回时把 `storagePath` 置空。
4. 中文文件名必须 ASCII 化后加 `filename*=UTF-8''` 双写法——曾经因为中文导致整个 `Content-Disposition` 头被丢弃。

### E-3 SQL 注入怎么防的？

全部走 MyBatis `#{}` 预编译占位符，**没有使用 `${}` 拼接**。
趋势图的分组粒度（day/week/month）由服务层白名单常量决定，SQL 内部用静态分支选择，不存在注入面。

## F. 部署与运维

### F-1 Docker / K8s 是只写了配置文件吗？

不是，都真跑过：Compose 四容器 healthy 并完成业务链路（含文件上传下载、容器删除重建后文件仍在）；
K8s 清单部署到 kind 集群 v1.31.0，四个 Pod 全部 `1/1 Running`；CI 用 act 在本地实跑两个 job 均通过。
过程中踩到的坑都已写入文档：K8s 里 `$(VAR)` 未被展开导致 Redis 口令为空和探针 WRONGPASS、
内置 K8s 镜像拉取失败改用 kind、act 缺 Maven 与 token 等，详见 `deployment.md`。

### F-2 为什么不做微信小程序？

评估后决定不做，理由写在 `docs/uniapp-evaluation.md`：

1. **技术不可用**：Element Plus、html5-qrcode、vue-router、localStorage 这四项在小程序端全部不可用，
   前端基本等同重写，工作量约 5 人日。
2. **硬前置缺失**：需要企业主体 AppID 与已备案的 HTTPS 域名，个人资源和课程周期内不具备。
3. 移动端已用 H5 响应式交付，能覆盖扫码打卡的核心场景。
   **做一个跑不起来的小程序，不如把一个能跑的 H5 做扎实。**

## G. 收尾类问题

### G-1 这个项目还有什么没做完的？

主动说：**不做掩饰反而加分**。

- 模块 E（请假/加班审批）共 7 条需求已在开工前决议暂缓，表结构预留但业务代码不实现；
- 真实人脸、生成式 AI、地图可视化三项受外部授权/Key 限制，走的是**明确标注的可插拔降级**；
- 小程序评估后决定不做；
- 没有 E2E 测试、没有做并发压测。
这些全部列在 `known-issues.md`，每一条都有原因和处理方式。

### G-2 如果给你更多时间，你会先做什么？

按优先级：

1. **真机扫码流程 + 移动端 E2E 测试**——目前用手动输入兜底，真场景还是要验证一次；
2. 本机已可按 `setup-guide.md` §3.5 用硅基流动启用生成增强；继续打磨提示词与评测；
3. 拿到 SDK 授权后替换人脸识别实现（接口已就绪，改造清单已写好）；
4. 补 E2E 与并发压测。
